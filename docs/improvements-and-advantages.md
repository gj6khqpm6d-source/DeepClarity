## 核心流程：预搜索驱动的澄清判断

```
用户提问
  │
  ▼
┌──────────────────────────────────────────┐
│ 预搜索（fork原创，上游完全没有）            │
│ LLM生成1-3条查询 → 程序化搜索             │
│ → 压缩≤12000字符 → pre_search_context     │
└──────────────────┬───────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────┐
│ 五维打分（LLM输出，结构化schema）           │
│                                          │
│ ① subject_clear    研究主题是否明确        │
│ ② scope_clear      研究边界是否明确        │
│ ③ audience_clear   目标受众/深度是否明确    │
│ ④ timeframe_clear  时间范围是否明确         │
│ ⑤ search_anchored  预搜索能否锚定主题(bool)│
└──────────────────┬───────────────────────┘
                   │
                   ▼
┌──────────────────────────────────────────┐
│ 代码决策（确定性规则，不是LLM自判）         │
│                                          │
│ subject=vague → 必问（主题没搞清楚）        │
│ 次维度≥2个vague + 无锚定 → 问              │
│ 单维度模糊 → 不问，写成假设推进             │
│ 已答过一轮 → 只有subject仍vague才问        │
│ 硬上限3轮 → 强制推进                       │
└──────────────────┬───────────────────────┘
                   │
          ┌────────┴────────┐
          ▼                 ▼
     追问（带假设）    直接进入正式研究
                         │
                         ▼
                supervisor拆任务
                researcher联网搜索+向量记忆
                notes压缩
                最终报告
```

### 五维决策规则速查

| 维度 | 类型 | 判断依据 | 什么情况vague |
|------|------|----------|-------------|
| subject_clear | clear/partial/vague | 读用户原话 | "研究AI"→vague；"LSTM门控机制"→clear |
| scope_clear | clear/partial/vague | 读用户原话 | "LSTM"→vague；"LSTM入门原理"→partial |
| audience_clear | clear/partial/vague | 读用户原话 | 未说明→vague；"零基础"→clear |
| timeframe_clear | clear/partial/vague | 读用户原话 | 未说明→vague；"2024年"→clear |
| search_anchored | true/false | 预搜索结果 | 搜到相关内容→true；搜不到→false |

**预搜索贡献第五维，前四维靠模型读原话。** 预搜索的价值不是"搜到了什么"，而是"搜到的东西能不能锚定住主题"——这就是 search_anchored 这个布尔值的含义。

## 二、上游已有什么 / fork 原创了什么(避免讲错)

| 能力 | 上游 HEAD | 本 fork | 归属 |
|------|-----------|---------|------|
| 澄清节点 | 有:`clarify_with_user` + `allow_clarification`,让 LLM 输出 `need_clarification` 布尔**自判**要不要问 | 重写为:预搜索锚定 + 五维打分 + 代码规则定夺 | 上游有,机制被本 fork 替换 |
| 预搜索 | **无**(`_run_pre_search` / `pre_search_prompt` 均不存在) | LLM 生成 1-3 查询→程序化搜索→压缩≤12000 字符 | **fork 原创** |
| 五维打分/规则/上限 | **无**(`AmbiguityAssessment` / `max_clarification_rounds` 均不存在) | subject/scope/audience/timeframe+search_anchored;确定性规则;硬上限 | **fork 原创** |
| 追问/推进标记、超时降级、收敛、降并发、向量记忆 | **无** | 修复 #4/#5/#6 + 向量记忆 | fork 原创 |
| checkpointer 持久化 | 平台部署时自动注入;本地代码未传 | `compile(checkpointer=MemorySaver())` 补上本地路径 | fork 补齐本地缺失 |

> 一句话:**澄清节点上游有,但它是"LLM 自判要不要问"的不可控版本;预搜索、五维打分、规则决策、硬上限——这些全是 fork 原创。** 核心贡献不是"发明澄清",而是"识别出上游失败模式(模型自判→死循环),用可审计的确定性设计替换它"。

### 补注:预搜索是全项目最大的亮点,但有两个已知边界

- **为什么是亮点**:它是"在不确定中敢推进"的底气——LLM 生成查询 → 程序化预搜 → 压缩为 `pre_search_context` → 变成第五维 `search_anchored`。它把"问题模糊但我能自己搞懂"这个判断自动化,是 `search_anchored` 这套设计的枢纽。
- **边界 1**:native search(Anthropic/OpenAI)工具的搜索是 dict、不可程序化调用 → `_run_pre_search` 返回 None,锚定退化为无。
- **边界 2**:搜索服务故障(如 DDG 限流)时预搜索为空 → `search_anchored=False` → 澄清走向保守。
- **已论证、未落地的增强**:预搜索失败时降级为"用模型知识生成锚点摘要",让 `search_anchored` 在搜索失败时至少反映"模型对主题的理解",而不是直接 false——把亮点从"有条件"变成"无条件"。列入 ISSUES.md 遗留项。

## 三、逐项说明(根因 → 方案)

### 1. 澄清判断节点(修复 #1)
- **上游问题**:无确定性澄清决策,LLM 自主判断"要不要再问" → 倾向多问,追问循环实测 3-4 次不进研究。
- **方案**:"**LLM 只打分,代码做决策**"。首轮预搜索一次(LLM 生成查询→程序化搜索→压缩≤12000 字符)作锚定;LLM 输出五维打分(subject/scope/audience/timeframe + search_anchored);代码规则定夺:主题必问、多维模糊且无锚定才问、单维模糊写成假设推进;`max_clarification_rounds=3` 硬上限兜底。
- **价值**:决策可预测、可审计、可调参;预搜索有锚定时少打扰用户。

### 2. 状态持久化(修复 #2)
- **根因**:`compile()` 未传 checkpointer → `thread_id` 无效,每轮状态全新:历史只剩一条、`clarify_count` 不累加 → 连硬上限都失效,循环跑不掉。
- **方案**:`compile(checkpointer=MemorySaver())`(进程内内存,本地够用;平台部署自动注入自己的,无副作用)。附带:`pre_search_context` 跨轮复用不再重搜。
- **陷阱**:改完图逻辑必须重启进程(Streamlit 重跑脚本 ≠ 重载模块)。

### 3. 搜索限流分层容错(修复 #3)
- **上游问题**:预搜索失败被 `try/except` 静默吞掉,DDG 限流时用户无感知。
- **方案**:一句话——**看得见失败 → 分层处理 → 重试有上限、跳过不卡死 → 最坏降级兜底**。
  - 预搜索=必要输入:重试 3 次、退避 2s/4s,仍失败才降级为无锚定打分;
  - 研究搜索=增强输入:单查询级容错,记 warning 继续,全部失败才抛异常;
  - `DDGS(timeout=5)` 防黑洞挂死。

### 4. 追问/推进 UI 区分(修复 #4)
- **根因**:clarify 节点既输出"追问"也输出"推进"verification,app.py 全标成"🤔 Agent"。
- **方案**:追问消息带 `is_clarification_question` 标记;app 据此只把真追问当成"等待用户回答"。

### 5. 评估调用超时降级(修复 #5)
- **根因**:澄清评估的 LLM 调用无超时,API 瞬时无响应时 `astream` 在产出第一个事件前卡死,前端零反馈(表现为"既不追问也不出研究内容")。
- **方案**:评估调用包 `asyncio.wait_for(..., clarification_assessment_timeout=60s)`;超时→warning + 构造"按假设推进"的降级评估,不追问、不挂死;app 一开始即显示"🧠 分析中"。

### 6. 追问收敛 + 降并发(修复 #6)
- **根因**:1) 无搜索锚定时次维度模糊每轮触发追问,已答还问;2) 研究并发(5 单元 × 工具全并行 gather)对 DDG 突发打请求,加重 IP 封禁。
- **方案**:已答 ≥1 轮后次维度模糊不再追问,仅 subject 仍模糊才问;`max_concurrent_research_units` 5→2 + 新增 `max_concurrent_tool_calls=2`,工具执行 `asyncio.Semaphore` 限流。

### 7. 向量记忆(本次新增)
- **目的**:网页读到即 embed 进线程级索引,`recall_from_read_content` 语义回看原文/片段,补"摘要即终点"短板。
- **方案**:`fastembed`(ONNX,免 torch)+ `BAAI/bge-small-zh-v1.5`;纯 numpy 余弦;任务级、周期结束清空;纯增强层,embedding 挂了图照常跑。
- **定位**:DDG 只存搜索片段、Tavily 存整页正文;机制就绪,切 Tavily 自动升级。

### 8. Streamlit 本地 UI(app.py)
- 上游主推 LangGraph Studio/平台;本 fork 提供本地 Streamlit 多轮对话界面,`thread_id` 按会话稳定,开箱即用。

### 9. 工程记录(ISSUES.md)
- 每个问题固定结构:总览 → 针对/根因/方案/涉及/验证/陷阱 → 遗留项。既是测试日志,也是面试能逐条讲的叙事素材。

## 五、最突出的三大优势(面试重点)

### 量化依据(2026-08-17 实测,单查询 LSTM 门控区别,Tavily+deepseek)

| 指标 | fork_full(澄清+预搜索) | baseline(无澄清) | delta |
|------|------------------------|------------------|-------|
| completeness | **5/5** | 4/5 | **+25%** |
| relevance | 5/5 | 5/5 | — |
| structure | 5/5 | 5/5 | — |
| 报告长度 | 8,054 字符 | 5,719 字符 | +41%更全面 |
| **成本** | **$0.118** | $0.159 | **便宜 26%** |
| 耗时 | 220s | 221s | ≈相同 |

> **结论:澄清机制(预搜索+打分+代码决策)同时提升质量并降低成本**——更准方向=更完整报告+更少浪费 token。后续可用`SEARCH_API=tavily`+充足余额扩大样本。

### 优势 1:决策可断言、可审计(对质量最根本)
"LLM 打分、代码决策"把**不确定的模型行为**和**确定的产品逻辑**分离:
- 五维打分可测(单测断言规则),`clarify_count` 有上限兜底,循环必然终止;
- 每一条修复都是"确定性可验证"的,不是"看起来更聪明"。
> 这比"更准的提示词"高一个量级——它是**把 agent 的不确定性关进笼子**。

### 优势 2:韧性——看得见失败、扛得住真实环境(对可靠性最根本)
- 三层容错:预搜索重试、研究单查询容错、最坏降级兜底;
- 超时:评估 60s 降级,不静默挂起;
- 并发:限流器防突发封禁;
- 一句话:**能力可以退化,但流程永不走死**。

### 优势 3:两层记忆(对长任务最根本)
- 线程级 checkpointer:对话状态真实累积;
- 向量语义记忆:读过的能按意思找回,补"摘要即终点"短板。
> 上游只有第一层,且依赖平台;本 fork 两层都有,且本地原生。
